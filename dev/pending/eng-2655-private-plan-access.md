## ENG-2655: private work plan access guard checks membership, not just "signed in" (2026-10-26)

`getPredefinedWorkPlan` (by title) and `createSessionWithPlan` guarded a private plan with `!result.user` while commenting "ownership/org-membership". The candidate lists they search were already limited to the caller's own and org members' private plans (as are `applyPredefinedWorkPlan`, the Emma recommend/accept tools and the MCP list/launch tools via `predefinedWorkPlanResolver`), so no live leak was found; the guard itself was a no-op for signed-in users. It now requires the plan to be in the caller's own/org private set, so a private plan reaching the system/public lists (stale index) is refused with 403. Ownerless private plans (the admin create route sets no `ownerId`, by design - "nobody launches it as an admin") are in no owner partition, so no user can read or launch them; they stay admin-managed via `/api/admin/work-plans`.
