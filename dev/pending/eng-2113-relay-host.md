## ENG-2113: the login host serves a tool relay (protocol 4) (2026-10-28)

- **What changed.** The worker can now give a customer's Claude CLI its tools without an HTTP bridge URL or token. Per turn the host starts the CLI with a stdio MCP server (`deploy/aw-relay-shim.js`, shipped in the build). The shim connects to a per-turn unix socket, `<relayRoot>/<uid>/<random 128-bit id>/relay.sock` (`/run/aw-relay-<env>`), which systemd binds READ-ONLY into that one unit at the fixed path `/run/aw-relay/relay.sock`. The unit must be the `PrivateNetwork=yes` shape: building a unit with a relay bind without it throws. Another turn's relay path is absent from the unit's mount namespace. Residual risk: this is not process isolation for the SAME uid: a process of the same uid in another unit can probably reach `/proc/<pid>/root/run/aw-relay/relay.sock` (no `PrivatePIDs` before systemd 255; the worker has 252). Same-uid turns are one trust domain (one customer's own login, own-chats-only plan route); different uids are separated by the mount namespace and the 0700 directory ownership. Use `PrivatePIDs=yes` once the worker runs systemd >= 255.
- **Wire (PROTOCOL_VERSION 3 -> 4; not deployed anywhere before this, so no compatibility shims).** `turn.run` takes `tools` INSTEAD of `bridgeToken`: the OPEN set at the start of the turn, `[{name, description, inputSchema}]` (closed schema, no flags). Emma opens a chat with only the foundation tools (+ `install_skills`, about 93 KB of definitions) and adds a skill's tools when the model installs the skill; the plan route does the same. `turn.toolResult` carries the tools made available BY THAT CALL: `{operationId, content, isError?, images?, tools?: [{name, description, inputSchema}]}`. Rules: a name already visible is a no-op (idempotent for a retrying backend, the first definition stays); a name that differs from a visible one only in case, a `aw_relay_` prefix in any case, an over-long name, a bad schema or description, or anything past the CUMULATIVE per-turn caps (every tool visible so far) refuses the whole answer with `EINVALID` (`tools:<reason>` from the route, `tools_invalid` / `tools_limit` from the host) and the operation stays PENDING, so the backend retries without them. The shim adds accepted tools, sends `notifications/tools/list_changed` and waits up to 3 s for the CLI to re-list before returning that call's result, so the model can call them in the same turn. Names: `^[A-Za-z0-9_][A-Za-z0-9_-]*$`, at most `TOOL_NAME_MAX_CHARS` = 53 (64 minus the 11 characters of `mcp__emma__`, derived from the server name; the model API refuses a longer qualified name and the whole turn fails). Limits (`TOOL_LIMITS`, cumulative per turn): 600 tools, 1 MiB in all, 48 KiB per description, 32 KiB per schema: DoS guards at about 2x the real registry, NOT a tool budget (measured 2026-10-29: 271 tools, about 503 KB, largest description 24,232 bytes, largest schema 15,084 bytes; a test loads the real registry, delivers all of it in steps on top of the foundation set and fails if it loses 1.5x headroom). The legacy shape (`bridgeToken`, no `tools`) behaves exactly as under 3; both together, or neither, is `EINVALID` (`tools:bridge_and_tools_mixed` / `tools:bridge_or_tools_required`). A new turn event `tool-call {operationId, messageId, name, input}`: the host generates a 128-bit `operationId` per relay request; the shim's own call id stays on the socket. The stream-derived `tool-use`/`tool-result` events stay informational and are never registered as operations. Images on a result: at most 4, png/jpeg/webp/gif base64, 2.5M chars each and 6M in all; the body cap of that route is 8 MiB, as is `turn.run`'s, every other route stays at 5 MiB. A result for an aborted turn is `ESTALE turn_aborted`; for an operation that is unknown, answered or expired, or a turn that has finished or never existed, it is `ENOTFOUND operation_unknown` (never a bare `ENOTFOUND`, which means "no such connection"); for one the provider already timed out it is `ESTALE result_lost`. All three mean "result lost": the backend persists the outcome from its ledger and tells the model.
- **Limits on the socket.** Shim -> host frames at most 1 MiB, host -> shim at most 8 MiB, newline-delimited JSON, 15 s without a complete frame drops the connection (the shim pings every 5 s), one connection at a time and 16 per turn, a token bucket per turn, one pending call per turn, unknown frame types and frames carrying any field beyond `{type, callId, name, args}` are refused. A call's clock starts when it arrives and lasts the turn's remaining time to its `deadlineMs` (host default 120 s only when the turn has no deadline); the shim sends `notifications/progress` every 15 s while a call is pending. Nothing from a frame is ever logged; the shim writes only fixed codes to stderr.
- **Deploy order.** The worker deploys first (an old worker refuses `tools`). A backend whose accepted worker protocols are only {2, 3} reports a worker at 4 as a mismatch, so `loginHostProvider.ACCEPTED_WORKER_PROTOCOLS` now includes 4 (one line, forced by the shared `PROTOCOL_VERSION` constant): that backend change must be live BEFORE the worker is deployed. New config keys `claude.relayShimPath` (default exists) and `claude.nodePath` (REQUIRED, no default: `/usr/bin/node` is a symlink on the worker; the prod template sets the shim to the release directory and `nodePath` to the REAL `/opt/aw-node/v<NODE_VERSION>/bin/node`, because `/usr/bin/node` is a symlink on the worker and the start-up trusted-path check refuses symlinks; `install.sh` fills `@@NODE_VERSION@@`) are a closed-schema addition: install the new host and its config together, which `install.sh` does.
- **Not in this PR.** The HTTP bridge, the bridge token, the egress exemption for the bridge and the legacy request shape stay (removed in PR 3). The backend half (using `tools`, executing `tool-call` out of band, `turn.toolResult`) is a separate PR.

- **Hostile input (security review).** The host no longer throws on data a customer's unit controls: shim frames deeper than 33 levels and CLI stdout lines deeper than 64 are dropped before parsing, informational stream values deeper than 32 / larger than 1 MiB are replaced by a fixed marker (a `tool-call` input is refused, never truncated), nothing stringifies shim/CLI data, every callback is guarded, a shim that never reads is cut at two queued frames, violation logs are throttled, and a last-resort handler exits 1 with a fixed-code line. `turn.toolResult` is a breaking reshape of the protocol-3 route (not additive): `ok` became `isError` and the schema is strict; nothing called it. The backend must size `turn.toolResult` content by serialized BYTES, not characters. `install.sh` now runs the host's trusted-path check on the rendered config (symlinked node path, shim ownership) BEFORE the switch. Crash-loop analysis and the full list are in `deploy/README.md`.

- **Limits on the plan route that in-process Emma does not have.** A `tool-call` whose arguments exceed 1 MiB (the shim-to-host frame cap) is refused: the shim answers the CLI "The tool arguments were too large." and the call never reaches the backend. A relay frame nested deeper than 33 levels is refused the same way (the connection is dropped). Stream announcements of tool inputs over 1 MiB lose their exact-input match and are matched by name only; a tool input over 1 MiB or 32 levels deep appears in the informational `tool-use` event as `{"_truncated":"size"|"depth"}`. The `/usr/bin/node` link is flipped only after the pre-switch trusted-path check of the rendered config, so a refused release changes nothing on the machine. The last-resort crash handler logs a fixed code only (no stack, by design): diagnosing a real crash needs a reproduction.

- **Rollback order.** Roll the backend back (or switch its relay off) BEFORE rolling the worker back to protocol 3, otherwise relay turns fail with `EINVALID` until the backend's protocol re-check (10 min). A `turn.toolResult` retried after its first delivery succeeded answers `ENOTFOUND operation_unknown` (the operation was consumed; by design: treat it as delivered). `install.sh` also checks, before the switch, that a customer uid can execute the pinned node and read the shim.

- **Event sizes and per-turn caps (round 5).** A CLI event is the customer's data: a `rate_limit_event` is cut to at most 16 windows and short status tokens (a 17 MB hostile line normalized in 790 ms before, ~100 ms after, and was forwarded as a 256-byte-weighted event of up to 21 MB; now every event weighs its real payload); an assistant or user message looks at its first 32 content blocks (MAX_BLOCKS_NORMALIZED and MAX_BLOCKS_PER_EVENT). Per turn: at most 500 relayed calls (`call_limit`), 16 connections, 8 MiB hashed for matching, and 32 refused connections before the relay listener is closed. The CLI stdout is a flood-limited stream (`stdout_flood` kills the CLI) that forwards only complete JSON object lines.
- **Residual risk, measured later.** A process of the same uid in another unit may reach a relay socket through `/proc/<pid>/root`; this is documented, not fixed (needs `PrivatePIDs=yes`, systemd 255+, the worker has 252). Live group B on the test box measures it.

- **Unified per-turn CPU meter (final security rounds).** The host is one event loop shared by every customer, so cost is accounted in what is actually scarce: MILLISECONDS OF EVENT-LOOP TIME, per turn (`relay/cpuMeter.ts`): a token bucket, burst 500 ms (it was 2,000 ms until the concurrent-turns review: see the next bullet), refill 50 ms per second (5% of the loop). When it is empty the CLI is killed (`cpu_budget`) and one throttled line is logged. What is metered, by the real elapsed time of the synchronous section: (1) the whole of `LineLimit._transform` INCLUDING the downstream push (readline, the runner's handleLine, JSON.parse and the session's callbacks all run inside it); (2) the child's stderr, through a guard that is metered, read- and byte-limited (reads: burst 2,000, 200/s; bytes: 1 MiB burst, 64 KiB/s) and hands the runner only the LAST 8 KiB, when the stream ends (`stderr_flood`); (3) the session's per-event work (nested inside (1): only the outermost section charges); (4) every read on the relay socket (scan, parse, validate, the adapter's onCall) and the answer path (two stringifies of up to 8 MiB). A tiny read also costs about 0.08 ms OUTSIDE any timed section (socket, pipe, Transform, readline: measured 0.07-0.09 ms); that fixed cost is charged to the meter on every read, and the sustained read rate per stream is 200/s (burst 2,000), where honest streams do a handful. On a trip the raw pipes are UNPIPED AND DESTROYED before the kill (production: SIGTERM, up to 10 s of grace): a writer that survives it costs the host nothing more (measured utilisation after the trip 0.00-0.02, down from 0.96-0.99). The per-vector buckets (reads, junk lines and bytes, event lines, event cost units = bytes + 64 per value, normalized events 2,000 burst / 200 per second per turn, 32 content blocks per message (a drop is logged once, `event_blocks_dropped`), 64 MiB of answered bytes per turn) stay as cheap early filters in front.
- **Numbers.** Honest turns: thousands of 0.05-0.2 ms events, and the odd big echoed result. The scan skips string bodies in bulk, so a 12 MB image echo now costs the meter about 60-70 ms (about 5 ms per MB; it was about 280-350 ms, 480 ms under load): five back-to-back 12 MB echoes (60 MiB, inside the 64 MiB event byte burst) spend about 240 ms, and ten 8 MB echoes spread over 60 s (mocked clock) are never killed, (honest: at most 5 such echoes in a row, and they do not trip a 500 ms burst either). Hostile turns, measured through the real adapter with real child processes: one-byte and 64 KiB junk, whitespace, valid-event-string and stderr floods are killed in 20-60 ms of wall time at 80-135 ms of loop; a 950 B/s one-byte trickle on stdout AND stderr is killed in about 3 s (loop active 390 ms); ten such trickles at once are all dead within about 3 s at 0.41 utilisation while alive on an idle machine and 0.5-0.65 with other jobs running.
- **Capacity, honestly.** A flat-out hostile turn is killed within about 3 s, having cost at most about 0.5 s of loop (the burst) plus 5% afterwards. A turn that PACES itself at its allowance (5% of the loop) is never killed: with `maxTurnsPerHost` = 12 such turns the host can lose about 60% of its loop to them, and it takes about 20 turns pacing at their allowance to saturate it. That is the design's bound (the allowance is the price of being allowed to stream at all); the limit on concurrent turns is the cap on it. NOT metered by time: the manager/HTTP consumer side of the event queue (it runs outside the adapter) and the HTTP body parse of an answer; they are bounded by the events-per-second bucket, the per-event size caps and the answered-bytes budget.
- **Event sizes.** A `rate_limit_event` keeps at most 16 windows and short status tokens; a message looks at its first 32 content blocks; the queue weight of every event is its real payload. Per turn: at most 500 relayed calls (`call_limit`), 16 connections, 8 MiB hashed for matching, 32 refused connections before the relay listener is closed, 64 MiB of answered tool results.
- **Residual risk, measured later.** A process of the same uid in another unit may reach a relay socket through `/proc/<pid>/root`; documented, not fixed (needs `PrivatePIDs=yes`, systemd 255+; the worker has 252). Live group B measures it.

- **A second CLI result limit: the per-tool persistence threshold (live finding, CLI 2.1.294, Haiku and Sonnet).** `MAX_MCP_OUTPUT_TOKENS` (156,400 in the unit's environment) is not the only thing that decides whether a tool result reaches the model whole: the CLI also saves a result above a PER-TOOL threshold to a file ("Output too large ... Full output saved to: ...") and gives the model only a ~2 KB preview. A 150 KB result arrived as a preview even with the token limit raised. An MCP server raises the threshold per tool with `_meta: {"anthropic/maxResultSizeChars": N}` in the tool's `tools/list` entry (the key is in the CLI binary). The relay shim now puts it on EVERY tool it lists, the open set and tools added by answers (`addTool` is the single place), with N = `RELAY_RESULT_MAX_BYTES` (300,000: the largest result the backend ever posts). The shim is standalone, so its constant carries a "must match" comment and a test keeps the two equal; a stdio test checks every listed tool has exactly that value. Security: the threshold only decides persist-or-not for text the backend already capped; a result at or below N is never written to disk by the CLI; above N (not reachable: the backend cuts at N bytes and N is in characters, so bytes >= characters) the CLI would write the text to its session tool-results file inside the unit's own scratch HOME (private tmp, removed with the unit, written exclusively, refusing links and files with other names) and show a preview. A unit cannot inject a result: answers come from the backend through the host.

- **Eight concurrent valid-but-expensive turns (final security review F1).** A stream announcement of a tool call (the assistant message that precedes it) whose input is over 64 KiB is no longer canonicalised or hashed (canonicalising a 116k-key object took ~0.6 s of loop): it is recorded by NAME only, the same rule as a call's own arguments, and a call is tied to it only when it is the only announcement of that tool. The announcement's size is estimated only up to that limit (the exact size of a 1 MiB input cost ~100 ms to learn). The CPU meter's burst went from 2,000 ms to 500 ms: a turn can take at most 0.5 s of loop at once (plus the section that crosses it) instead of 2 s. Measured with 8 real turns, each printing a `tool_use` line with 100k three-character keys 40 times, 50 ms apart (host loop busy time / longest single stall / an honest turn's event delay p50 and p99): before 25.6-28.9 s / 3.0-4.0 s / 1.7-2.6 s and 3.4-4.7 s; after the hashing change alone 26.3 s (the 2 s burst per turn dominates); after the 500 ms burst 6.1-7.4 s / 1.6-3.0 s / 0.45-1.06 s and 1.96-3.4 s (the stalls are several queued reads of different turns processed back to back; each read of such a line still costs ~300 ms: parse 43, bounded-value copy 167, queue weight 94). A 15.5 MB honest text line, twice, in each of 8 turns: 3.8 s of loop in all, longest stall 0.27 s, none killed. No pipe pausing was added.
