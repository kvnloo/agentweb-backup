## ENG-2113: the login host serves a tool relay (protocol 4) (2026-10-28)

- **What changed.** The worker can now give a customer's Claude CLI its tools without an HTTP bridge URL or token. Per turn the host starts the CLI with a stdio MCP server (`deploy/aw-relay-shim.js`, shipped in the build). The shim connects to a per-turn unix socket, `<relayRoot>/<uid>/<random 128-bit id>/relay.sock` (`/run/aw-relay-<env>`), which systemd binds READ-ONLY into that one unit at the fixed path `/run/aw-relay/relay.sock`. The unit must be the `PrivateNetwork=yes` shape: building a unit with a relay bind without it throws. Other turns' sockets do not exist inside the unit, for the same uid or another.
- **Wire (PROTOCOL_VERSION 3 -> 4).** `turn.run` takes `tools` (a bounded manifest: names `^[a-z0-9_]{1,48}$`, no `aw_relay_` prefix, at most 200 tools / 512 KiB in all, 4 KiB description and 16 KiB schema each, optional `locked`) INSTEAD of `bridgeToken`. The legacy shape (`bridgeToken`, no `tools`) behaves exactly as under 3; both together, or neither, is `EINVALID` (`tools:bridge_and_tools_mixed` / `tools:bridge_or_tools_required`). A new turn event `tool-call {operationId, messageId, name, input}`: the host generates a 128-bit `operationId` per relay request; the shim's own call id stays on the socket. The stream-derived `tool-use`/`tool-result` events stay informational and are never registered as operations. `turn.toolResult` is now `{operationId, content, isError?, images?, unlock?}` (images: at most 4, png/jpeg/webp/gif base64, 2.5M chars each and 6M in all; `unlock` names `locked` manifest tools to reveal); that route's body cap is 8 MiB, every other route stays at 5 MiB. A result for an aborted turn is `ESTALE turn_aborted`; for an operation that is unknown, answered or expired it is `ENOTFOUND operation_unknown`; for one the provider already timed out it is `ESTALE result_lost`. All three mean "result lost": the backend persists the outcome from its ledger and tells the model.
- **Limits on the socket.** Shim -> host frames at most 1 MiB, host -> shim at most 8 MiB, newline-delimited JSON, 15 s without a complete frame drops the connection (the shim pings every 5 s), one connection at a time and 16 per turn, a token bucket per turn, one pending call per turn, unknown frame types and frames carrying any field beyond `{type, callId, name, args}` are refused. A call's clock starts when it arrives and lasts the turn's remaining time to its `deadlineMs` (host default 120 s only when the turn has no deadline); the shim sends `notifications/progress` every 15 s while a call is pending. Nothing from a frame is ever logged; the shim writes only fixed codes to stderr.
- **Deploy order.** The worker deploys first (an old worker refuses `tools`). A backend whose accepted worker protocols are only {2, 3} reports a worker at 4 as a mismatch, so `loginHostProvider.ACCEPTED_WORKER_PROTOCOLS` now includes 4 (one line, forced by the shared `PROTOCOL_VERSION` constant): that backend change must be live BEFORE the worker is deployed. New config keys `claude.relayShimPath` and `claude.nodePath` (defaults exist; the template sets the shim to the release directory) are a closed-schema addition: install the new host and its config together, which `install.sh` does.
- **Not in this PR.** The HTTP bridge, the bridge token, the egress exemption for the bridge and the legacy request shape stay (removed in PR 3). The backend half (using `tools`, executing `tool-call` out of band, `turn.toolResult`) is a separate PR.
