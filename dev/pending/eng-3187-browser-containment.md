## ENG-3187: the browser server no longer inherits the backend's secrets or working folder, and its navigate tool opens public pages only (2026-11-25)

**The problem.** The agent's browser is a Playwright MCP server that runs as a child process of the backend. `McpClientService.createStdioTransport` started it with `env: { ...process.env, ...resolvedEnv }` (since 2026-01-22) and no working folder, so the child had the backend's whole environment (login-token signing secret, AWS keys, Stripe and Slack keys) and the backend's own folder as its file root. Its `browser_run_code` tool runs the caller's code in a Node `vm`, which is not a security boundary: `page.constructor.constructor('return process')()` returns the host `process`. Any signed-in customer can drive that tool from their own chat. Chrome also runs with `--no-sandbox` (2026-03-12) and with site isolation switched off (2026-04-26, anti-detection work).

**What this change does (code only, `backend/src/mcp/client/playwrightContainment.ts` + `mcpClientService.ts`).**
- The browser server gets an allow-list environment (`PATH`, `HOME`, locale and temp variables, proxy and certificate variables, `PLAYWRIGHT_BROWSERS_PATH`, font settings, `LC_*`, `XDG_*`) plus whatever its own configuration sets. Nothing else. `MCP_PLAYWRIGHT_INHERIT_ENV=true` brings back the old behaviour (a rollback switch; it needs an environment change on the server).
- It runs in its own empty, owner-only folder under `/tmp/playwright-mcp-work/<pool>`, also passed as `--output-dir`. Playwright confines the browser's file tools to its working folder, so they no longer reach the backend's folder. The folder is removed with its pool and swept at startup if a hard kill left it behind (24 h).
- `--blocked-origins` lists the cloud metadata addresses. Playwright documents it as not a security boundary and not applied to redirects.
- `browser_navigate` is checked before the call, in both places a tool is registered: only `http:`/`https:` (and `about:blank`) are opened, and the host must pass `assertPublicHostname` (so `file:`, `view-source:`, `chrome:`, `data:`, `javascript:`, loopback, private ranges, link-local, local names and names that resolve to them are refused; an address that cannot be checked is refused). The refusal is worded for the model, is not retried, and the log line never carries the address.
- Other stdio MCP servers are unchanged.

**What it does NOT do (tracked in ENG-3187).** Code that escapes the `vm` runs as the same OS user as the backend and can still read `/proc/<backend pid>/environ` and the backend's files; a page that redirects to an internal address after the navigate check is not covered; `browser_run_code` itself is untouched (about 43% of browser-tool calls in the production log on 2026-11-25, and five internal tools depend on it: cookie persistence and tools, site sign-in, the reCAPTCHA solver, the X.com typing rule). The real fix is the browser server under its own OS user or container with the metadata address blocked for it (infrastructure), and a decision on model-driven `browser_run_code`.

**Rollback.** Revert the PR, or set `MCP_PLAYWRIGHT_INHERIT_ENV=true` to restore only the old environment.
