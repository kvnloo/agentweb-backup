## ENG-2465 / ENG-2464: re-point stored HubSpot contact ids on `contact.merge`, and a live-check script (2026-10-14)

**Why.** Since ENG-2171 the batched HubSpot push updates a lead by its stored `syncMetadata.hubspot_contact_id`. If the customer merges two contacts in HubSpot, that id points at the merged-away contact, so the lead would fail every push (`sync_failed`, id kept, nothing created). HubSpot documents a `contact.merge` webhook (`primaryObjectId`, `mergedObjectIds[]`, `newObjectId`, `numberOfPropertiesMoved`) and no API to find the survivor from a merged-away id, so the webhook is the only documented way to learn it.

**ENG-2465.** Both HubSpot webhook handlers (`routes/webhooks.ts` shared endpoint, `routes/crmWebhook.ts` per-list endpoint) now handle `contact.merge`: the lead holding a merged-away id gets `hubspot_contact_id` rewritten to the survivor (`newObjectId`, else `primaryObjectId`), other `syncMetadata` kept. In the shared endpoint the merge rides in the durable job payload (optional `merges` field, so already-queued jobs still process) and applies only to lists connected to that portal. Merges are applied before deletions in the same delivery, so a `contact.deletion` for the merged-away id no longer deletes the re-pointed lead. A lookup or write failure is logged and skipped, never thrown. Idempotent: after the rewrite the old id matches no lead.

**Not done / limits.**
- The customer must add the `contact.merge` subscription to the HubSpot app; nothing subscribes to it today, so until then merges are not seen. I could not confirm whether HubSpot also sends `contact.deletion` for the merged-away contact.
- If another lead in the list already holds the survivor's id, both now share it; the push handles that (same email collapses, different emails upsert by their own email).
- `getLeadByHubSpotContactId` is a bounded partition query (no index): a very large list can exhaust the page cap, in which case that merge is skipped with a warning.
- Not live-verified (no connected HubSpot); covered by unit tests only.

**ENG-2464.** `backend/scripts/hubspot-live-check.mjs` records the raw status and body of the contact edge cases HubSpot's docs do not describe (missing id, archived id, mixed batch, duplicate id, email collision, merged-away id, unknown property, upsert right after an email write) and whether `isContactGoneError` would classify each as "gone". It needs a HubSpot developer test account private-app token (`HUBSPOT_TOKEN`) and `HUBSPOT_SANDBOX_CONFIRMED=yes`, uses only `@eng2171.example.invalid` probes, and archives them in a `finally`. Its own offline test (`node --test backend/scripts/hubspot-live-check.test.mjs`) runs against a local fake and proves the script, not HubSpot. The card stays open until someone runs it against a real portal and pastes the output.

**Connect error (not in this PR).** The HubSpot connect failing for portals without Marketing Hub is a HubSpot app-config mismatch (marketing scopes registered as `conditionallyRequiredScopes` while we send them as `optional_scope`). `social` is documented as deprecated but `SOCIAL` broadcasts in the Emma HubSpot tool use it, so it is left in `marketingOnlyScopes`.
