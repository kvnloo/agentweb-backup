## ENG-2816: schedules a share-link visitor wrote run with the visitor limits; a visitor cannot stop the owner's turn (2026-11-17)

A share link runs the visitor's turn under the OWNER's userId, so a schedule a visitor created or edited (`manage_scheduled_chat`, `submit_scheduled_chat_variables`, `create_schedule_from_template`) was stored as the owner's own and its later runs got the owner's full tool set (reproduced 2026-11-05: a visitor-made schedule ran `save_memory` as the owner).

- **One new optional attribute:** `provenance`, a DynamoDB String Set on `AW-TaskSchedules` items only (no table, index, IAM or template change). Members are the tracked content fields a visitor last wrote: `startingMessage`, `keywords`, `requiredFunctionCalls`, `functionCallMinCalls`, `variables`, `variableValues`, `emailNotifications`. Absent on every existing schedule and never backfilled, so existing schedules behave exactly as before. A schedule is "marked" when the set is non-empty. Read it only through `readScheduleProvenance` (`utils/scheduleProvenance.ts`): a Set, an array and absent are fine, an unreadable value reads as marked. The db layer returns it as a sorted array.
- **Writes:** `updateSchedule` takes the non-stored `provenanceAdd` / `provenanceRemove` and puts `ADD` / `DELETE` in the SAME `UpdateExpression` as the content (one or the other: DynamoDB cannot ADD and DELETE one path in one expression). `createSchedule` takes `provenance` (omitted when empty).
- **Who wrote it:** `ctx()` passes `restrictionProfile`, `mcpFetch` signs it into the self-call JWT as `_rp`, `authenticateToken` sets `req.restrictionProfile` only from a verified `_svc` token. Second signal: an in-process marker per session id (`services/shareVisitorTurnMarker.ts`), set where a share route claims the generation lock and cleared when it is released. A write is a visitor's if EITHER says so; voice has only the claim. A restricted caller cannot use a pre-minted override token to change schedules (it cannot carry the claim).
- **Enforcement is live, in `executeTool`:** for a tool call in a scheduled run (session `pageIdentifier` `...|scheduleId:<id>`), if profile `share_visitor_schedule` (same block list as `share_visitor`, its own wording) would refuse the tool, the schedule is read CONSISTENTLY and the call is refused when it is marked or cannot be verified. Covers every run entry (cron, manual, test, variables submit, resume, retry, self-improve, approval resume, continuations) because they all end there. The schedule-writing tools get the profile in their context, so a marked run's own `manage_scheduled_chat update` is a visitor write and re-marks what it writes.
- **Marked runs:** refused tool names are dropped from `requiredFunctionCalls` / `functionCallMinCalls`, retries cap at 3 (not 20), and publish authorization resolves to UNAUTHORIZED (the legacy "never asked = authorized" default would otherwise read a visitor-written required `post_on_connected_account` as the owner's consent). Withhold reason `visitor_edited`.
- **Lifting only on positive owner evidence:** a real portal login (not a self-call, delegate or visitor write), per field, only when the field is in the request AND its value differs from the stored one (the portal posts the whole form, so a routine save lifts nothing). Or `POST /api/agent-mode/scheduled-chats/:id/adopt-visitor-edits` (owner login only, bound to `updatedAt`), which removes the whole set. No MCP tool body can write provenance or reach that route (source-scan test).
- **Stop route:** `POST /ishare/:id/stop` cancels only for the owner's own login, or when the running turn was started through a share route by a visitor. An ignored stop answers the same `200 {success:true}`, does not call `markProgressComplete`, and leaves no cancel flag. Until the portal sends the viewer's login on a conversable stop, an owner stopping their OWN turn from their share link is ignored (portal follow-up).
- **Known gaps (not closed here):** a template has no provenance, so a visitor-written template the owner later uses is unmarked; the emailed public variables link writes `variableValues` unmarked; approval-inbox and work-plan continuations of a visitor's SHARE session run without the share flag; schedules a visitor made before this shipped cannot be told apart (no backfill); the marker is per process and a visitor's stop in the instant between claiming the lock and recognising the owner can still cancel an owner turn.
