## ENG-2113: plan chat gets its tools through the worker's relay (backend half, PR 2) (2026-10-28)

- **What changed.** A plan turn on a worker that speaks protocol 4 no longer depends on the HTTP bridge URL. `ClaudeCodeBackend` sends `turn.run` with a `tools` manifest INSTEAD of `bridgeToken`; the worker's stdio shim turns the CLI's tool calls into `tool-call` events; the backend runs each one through the SAME `ToolBridge.callTool` the HTTP route uses (liveness check before every execution, the run's tool list, halts, ledger, write confirmation) with the run's internal token (which never leaves the process), and answers with `turn.toolResult`. The stream-derived `tool-use` / `tool-result` events stay informational: on the relay path they feed progress only and never execute or register anything.
- **Which transport a turn gets (exactly; fail closed).** `chooseToolTransport` in `claudeCodeBackend.ts`, decided right after the host client is found and BEFORE anything is opened: relay iff `protocolStatus() === "match"` AND `workerProtocol() >= 4` AND the bridge can be called in process; the HTTP bridge ONLY when status is `match` and the worker protocol is a KNOWN number below 4 (unchanged behaviour for an old worker). Everything else is refused with the typed, retryable `host_unavailable` stop, known to have run no tool (so the controller's "continue on AgentWeb credits" offer stays correct): status `unknown` (the first turn after a backend start, or the up-to-a-minute window after a failed 10-minute recheck), `mismatch`, or a 4+ worker without an in-process bridge. On a relay-capable worker a manifest with nothing to offer, or one the protocol schema would refuse, is the typed retryable `turn_failed` stop, also known to have run no tool. Why: on production the HTTP bridge URL is a zero-tool stub, so a silent fallback would answer with no tools and no error. A backend built without the `relay` dependency (tests) keeps the HTTP path; the production instance always has it. Log lines: `relay_refused cause=protocol_unknown|protocol_mismatch|bridge_not_in_process|manifest_empty`.
- **Files.** `relayToolDispatcher.ts` (out-of-band execution, identity from the turn's own closure, soft deadline, result-lost handling, image/size bounds), `relayManifest.ts` (manifest from the bridge tool list; names map by identity, anything outside `^[a-z0-9_]{1,48}$` or with the `aw_relay_` prefix is skipped and counted, never rewritten; oversize schemas skipped, descriptions cut to the byte limit, locked tools dropped first under the caps, `install_skills` never), `loginHostClient.ts` (`tool-call` event shape; `turnToolResult` raises `ToolResultLostError` for ESTALE / ENOTFOUND, never a `LoginHostError` ENOTFOUND, which elsewhere means "no such connection" and is destructive), `claudeCodeBackend.ts` (dual mode, settle before drain, `annotateLostResults`), `toolBridgeMcp.ts` (`listTools` / `callTool` passthroughs), `emmaToolBridgeExecutor.ts` (`resolveCandidateTools`: the entitled registry without the session's skill filter, offered as `locked`), `loginHostTurn.ts` (the wait for a free slot is abortable).
- **Result lost.** `ESTALE turn_aborted`, `ENOTFOUND operation_unknown`, `ESTALE result_lost` all mean the tool may have run. The outcome stays in the bridge ledger; the call id is recorded and the PERSISTED tool result gets `RESULT_LOST_NOTE`; an identical retry in the same turn gets the original result back (`REPLAY_NOTE`) instead of running again. Late records of a relay turn always carry the note (the worker's turn is over).
- **Deadlines.** `deadlineMs` stays the hard one (turn cap - elapsed - grace - busy wait, floor 30 s); the soft deadline is `min(75 s, deadline / 2)` earlier; after it no tool starts and the model is told to write its final answer.
- **Skills.** The model still chooses; the manifest carries the entitled tools that are not yet in the session's list as `locked`, and the `install_skills` result carries `unlock` = locked names the bridge's CURRENT list now offers. The bridge re-validates every call against its current list, so a locked tool cannot run before the install even if the worker emitted a call for it.
- **Never silent cuts.** A tool left out of the manifest or a description cut to the byte limit logs `relay_manifest_cut` with counts. `relayManifest.registry.test.ts` builds the manifest from the REAL registry (every skill) and asserts nothing is cut; it is SKIPPED until the host branch raises `TOOL_LIMITS` (today: 275 tools against a cap of 200, 8 descriptions over 4 KiB) and must be un-skipped with that merge.
- **Halts (SF1).** Once a halt is latched, the relayed answer that goes back closes the call group in the bridge BEFORE it is posted (what a tool-result in the stream does on the HTTP path), so a later call cannot join the halted group by reusing its message id. Consequence: because the worker hands over ONE call at a time, a same-message sibling of a halted preview is refused on the relay path (the HTTP path admits it within the latch window): stricter, one more confirmation round in that case.
- **Worker limits (SF2).** Past the call cap (400) or 16 operations in flight the worker is treated as misbehaving: its further calls are not run, not answered, not counted, the turn is interrupted (A16) and ends as a typed stop with what ran persisted. Progress is reported only for manifest names; repeated operation ids are not counted.
- **Delivered vs lost (S1).** Every executed call whose answer the worker did not ACCEPT is persisted with the note (a failed post, a post still in flight when the drain window ended, a call that finished after the turn). Residual, fails safe: a post that timed out after the worker had in fact accepted it is persisted with the note although the model read the result.
- **Known deviation: parallel read-only calls are serialized (S4).** The worker's relay keeps ONE pending operation per turn, so calls the CLI issues in parallel (several read-only tools of one message) reach the backend one after another: slower, same outcome. Removing it needs the host relay to allow N pending operations per turn (the shim already multiplexes call ids; `relayServer.ts` would keep a bounded map instead of one `pending` slot, with per-call timers), the backend dispatcher already runs concurrent calls (bridge: read-only concurrent, writes serialized per session).
- **Not in this PR / residual.** The halt-then-interrupt of A9 is not added (parity with the HTTP path). A replay of a lost result re-checks liveness through the bridge's tool list (a revoke in this process closes the run at once; one handled elsewhere is seen within the bridge's 5 s read-liveness cache).
