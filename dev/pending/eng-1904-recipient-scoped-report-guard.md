## ENG-1904: a non-admin recipient can receive an admin-run report when everything the run read was about them (2026-11-19)

The ENG-500 guard treats a scheduled report as sensitive when the run called ANY cross-account tool, and then only admins (plus the owner while still an admin) receive it. An admin who runs a report ON BEHALF OF a client therefore never reaches the client: the client is withheld and the report goes to the admin (reproduced 2026-11-19 on the test environment and on production in the owner's own accounts; production already shows it: a real schedule's delivery log has 6 withheld and 6 delivered). This adds one narrow, ADDITIVE path. **Switched off by default** (`SCHEDULED_REPORT_RECIPIENT_SCOPING=true` turns it on); with it unset, behavior is exactly today's plus a `[ENG-1904 shadow] would have sent a link-free copy ...` log line.

- **The rule (`services/scheduledReportScope.ts`, pure):** a withheld non-admin recipient gets a separate copy only if EVERYTHING the run read was about that recipient. Every tool the run used must be scopable (`monitor_lead_volume`, `read_client_meta_activity`, the three Meta tools, the two Google Ads tools) or a report builder that reads no tenant data (`install_skills`, `list_available_skills`, `resolve_skill`, `list_html_templates`, `create_html_from_template`, `perform_data_analysis`). Every scoped call, from every source (the assistant's `tool_calls`, the executed ledger in `metadata.toolCalls`, the tool-result rows), must name the recipient EXACTLY: an email (case-insensitive) or a user id, never a name, since the client-health family matches names by substring and takes the first hit. The saved tool RESULT's `client{userId,email}`, where present, must also be the recipient's, which catches a loose match. The Meta and Google Ads tools read the CALLER's own account when `client_id` is omitted (the admin's), so an unscoped call is not the recipient's. The multi-subject tools (`list_all_clients`, `get_users_by_lifecycle_stage`, `get_chat_history`, `get_registration_status`) and the internal-data tools (`get_session_transcript`, `get_user_by_id`, `inspect_client_usage` which returns the org's BILLING OWNER, `manage_user_notes`) stay admin-only for ever. Unreadable messages, unparseable arguments, an unresolved recipient, a deleted or missing account, and any error all answer "no". Recipient identity is the strongly consistent `getUserByEmailConsistent`.
- **What changes in the email send (`emailService.ts`):** `classifyAndResolveScheduledReportRecipients(sessionIds, recipients, { allowScopedRecipients })` returns an extra `scoped` list; `authorized` and `withheld` are exactly what the guard decided. Only the single-report send asks for it (the daily digest merges several runs and keeps today's rule). The admin's email is unchanged (checked by hashing the old and new output for an ordinary report and for a withheld-then-owner report: identical); its withheld banner no longer lists a recipient who did receive the report. The scoped recipient gets a SEPARATE email without the "Continue the Conversation" block (the session is an admin's, and its share view hides turns that used admin tools, so it is not proven safe for a customer) and without anyone else's address. The delivery log records both as delivered; a failed send of the client copy is `delivery_attempted` / `provider_error`.
- **Google Ads mirrors Meta:** `call_google_ads_api` and `call_google_ads_reporting_api` take the same admin-only `client_id` and were never on `CROSS_ACCOUNT_USER_DATA_TOOLS`. They are added to it and to `ADMIN_SCOPED_CROSS_ACCOUNT_TOOLS` (dropped for a verified non-admin owner, so a customer's own Google Ads report is unaffected; an admin-owned run that used them now counts as cross-account). Production scan 2026-11-19: no active schedule changes.
- **Not done, on purpose:** no recipient plan check (nothing in the delivery path checks a recipient's plan today; it belongs in the ENG-1880 Phase C opt-in); no change to the activation gates or the preflight (they see no arguments); the daily digest keeps today's rule; the optional `ownerIsAdmin` inconsistency at template create and admin resume is left alone. **Residuals, written down:** an admin-owned run also carries the admin's own account and org memory, which a tool-name check cannot see; `perform_data_analysis` can read the admin's own files; `notify_session`, Slack-triggered email and the model's own send tools bypass the guard entirely; the share link minted before the guard still goes to admins.
