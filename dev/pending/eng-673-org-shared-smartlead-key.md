## ENG-673: Smartlead pushes can use a connection a teammate shared with the org (2026-10-28)

Owner decision: a Smartlead API key is stored per user and can be shared with the org, and anyone in the org may push, release and control pushes through the portal and Emma using it. Until now the push used only the pusher's own connection and refused a teammate's shared one. `SmartleadPushService` now resolves the connection like the rest of the Smartlead code (`resolveSmartlead`): the caller's own first, else the single one a teammate shared; several candidates and none the caller's are never guessed between: the answer is 409 `choose_connection` with the candidates (`details: [{accountId, accountName, shared}]`) and the caller picks one by `accountId`. The run records whose key it was (`keyOwnerId`), and the worker and the hourly withdrawal sweep keep using that owner's key. Resume is now allowed to the key owner and to anyone the connection is still shared with (it was the pusher only); once sharing is withdrawn a member can no longer resume (403 `resume_requires_connection`), but anyone with edit access can still pause and cancel. The campaigns and preview results carry `connection: {accountId, name, shared}` so the screen and the Emma approval card say whose Smartlead account the contacts go into ("a teammate's shared Smartlead account ..."), because the emails go out from that account's mailboxes. The Emma tools accept an optional `accountId`. List edit access is still checked per person. No schema change. Un-sharing a connection also stops the teammates' pushes that use it: before each run of work the worker checks that the connection is still shared with the pusher, and otherwise pauses the run with `connection_unshared` (a key that is merely rejected is still reported as `key_rejected`).
