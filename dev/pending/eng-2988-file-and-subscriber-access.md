## ENG-2988: file access by key, and the public subscriber routes (ENG-2990, ENG-2991) (2026-11-16)

**What was wrong.**
- `GET /api/files/presign` (`key=` and `url=`), `POST /api/files/presign-batch`, `GET /api/files/content` and `POST /api/files/html` acted on any key of the file bucket for any signed-in user. Reproduced on the test environment with an organisation-less, non-admin user: it could sign, read, and overwrite another account's files (`html` saved over them).
- `GET /api/tasks/:taskId/subscribers` needs a login but returned the full subscriber records (emails, imported fields, email history, feedback) of any task to any signed-in user.
- The public `POST /api/tasks/:taskId/subscribers/join` wrote a row for any task id, with no rate limit and no confirmation, and sent a welcome email from the task owner's account to whatever address was typed. The public `POST /api/tasks/:taskId/resubscribe` reversed an opt-out from a task id and an email address alone.

**What changed: files.**
- `services/storageAccessPolicy.ts`: one policy for the four file routes, run on the exact key that is signed, read or written. Canonicalise (no dot or empty segments, backslash, control characters, over 1024 characters; `?` and `#` only where they were escaped in a URL path; a URL path is decoded once, a stray `%` is taken literally; one leading `s3:` is stripped), then decide by key shape: owner, same-organisation teammate (reads only: `users/<id>/files|brand|remotion`, execution files, task files under the knowledge-base share rule), real admin (not a delegated session, not an in-process tool call), else refused. An execution folder must belong to the task in the key (and if the execution lookup fails the answer is "try again", not a fall-back to the task). An id in a key that cannot be a real id (not letters, digits, `_` or `-`, or over 128 characters) is refused without a database lookup. `users/anon_*` (an anonymous visitor's plan session, which moves to their account at sign-up but keeps the key) is readable by any signed-in user and writable by an admin only.
- Answers: 404 "File not found." (the portal words 401/403 as "session may have expired"), omitted in a batch; 403 "You can view this file, but only its owner can change it." when a teammate tries to save over a file they can open; 503 "try again" when the check itself could not run (a lookup threw). Refusals are logged as `storage_access_denied` with the kind of file (a fixed list, nothing caller-chosen), reason and caller, never the key; a failed lookup as `storage_access_lookup_failed`.
- `/html` authorises the key the upload will really write (`uploadFileToS3WithPath` rewrites odd characters in the file name; `sanitizeS3Filename` is exported from `s3Utils`; a name that rewrites to `..` is refused). Signing uses the decoded key, so names with spaces or non-ASCII characters presign the right object (they signed the wrong one before). The unrouted `viewExternalFile` (an unchecked fetch of any URL, never mounted) is removed. New narrow read `taskDb.getTaskExecutionOwnerById` (owner and task id only) so an execution-file check does not read the whole execution row.

**What changed: subscribers.**
- List: task owner or admin only.
- Join (`POST /:taskId/subscribers/join`) is a double opt-in. The address must be a plain, strictly valid address of at most 254 characters (the old pattern backtracked badly: about 1.4 seconds for 20,000 characters, and the body limit is 50 MB). The task must exist. 10 attempts an hour per connection; per task and mailbox one confirmation per 30 minutes and per mailbox (plus-tags, case and Gmail dots folded) 5 an hour across tasks (both answer exactly like a normal sign-up, so the form cannot probe), per task 300, per task owner 600 and in total 3000 an hour (these answer 429 "try again in a little while" so nobody waits for mail that was never sent); the counters are in memory per instance and bounded; a failed send gives the slot back. An already-subscribed or opted-out address gets the same 202. Nothing is stored until the person confirms.
- Confirm: `GET /:taskId/subscribers/confirm?token=` (48 hours) only shows a page with a button (mail scanners and link previews open every link; HEAD changes nothing); `POST` on the same path subscribes (the welcome email follows). The page is sent with `Referrer-Policy: same-origin` and a content-security policy of `default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; frame-ancestors 'none'`. **It must not use the API-wide `no-referrer`**: under that policy a browser labels a form POST `Origin: null` even to the same site, and the app-wide CORS check rejects that with 403, so the button would never work (found in review; the same trap `routes/zoma.ts` documents). `subscriberConfirm.realApp.test.ts` boots the real app and posts with the Origin a browser would send for the page's own policy. A link sent before the person unsubscribed no longer works (compared with the opt-out time); the address is matched to an existing row in any letter case (rows are stored as typed), so the person is not added twice: that reads the task's address list narrowly (email, unsubscribed, unsubscribedAt), shares one read between simultaneous callers, keeps it 30 seconds, and re-reads the matching row before deciding (`services/subscriberLookup.ts`); and the insert is conditional so two simultaneous confirmations create one row.
- Unsubscribe is one atomic conditional update (`softUnsubscribe(..., { onlyIfActive: true })`) and returns a resubscribe token (24 hours) only to the call that really flips the row. An address that has already opted out, or a call that lost a race, gets none (otherwise anyone could mint one and undo the opt-out), and that call also gives the opt-out a new time (`refreshOptOut`), which voids any token someone obtained for the earlier opt-out (otherwise whoever unsubscribed an address a moment before the person did could undo the person's own opt-out). The token names the address exactly as stored (rows are case-sensitive) and the opt-out it undoes (`unsubscribedAt`): resubscribe checks both against the row, so a token cannot be replayed after the person opts out again or has been put back, nor carried to another spelling of the address; and the resubscribe itself is one conditional update (`resubscribe(..., { onlyIfUnsubscribedAt })`), so a re-opt-out between the check and the write is not reversed. The public unsubscribe and undo calls are limited to 60 an hour per connection. The subscriber reads in these routes are strongly consistent. The public status route returns only `{email, unsubscribed}`. Public routes answer 400 for non-text addresses and a generic message on a 500 instead of the database's.
- Tokens are signed with an HMAC-derived key (not the login secret), HS256 only, bound to purpose, task and lower-cased email.
- The confirmation email: from the task's own sender the subject carries the task name (one line, 80 characters); from the system address the subject is fixed ("Please confirm your subscription") and the name is bounded in the body; it reports whether it sent. The address pattern also refuses leading, trailing and doubled dots and accepts punycode domains.
- Customer portal (separate PR, deploy it first): the unsubscribe page keeps the token for the undo and offers it only to the person who has just unsubscribed; the embed snippet shows the server's "check your email" message; a presign 404 opens the file directly, only for an https address of our own bucket (a temporary stopgap so signed-in people viewing a shared chat can still download); the artifact panel says why when a save is refused.

**Mail-relay risk that is only reduced, not removed.** The join form sends mail from the task owner's connected sender (or from AgentWeb's system address) to an address anyone types. The limits above (10 an hour per connection; per address; per mailbox; per task 300, per owner 600, in total 3000 an hour) bound it, but there is no CAPTCHA or signed form token, so a determined attacker with many connections can still use up a task's, an owner's or the whole service's allowance (the form then answers 429 for everyone) or send a bounce trap to an owner's domain. From the system address the task name is not printed at all. Recommended follow-up (a product decision, not made here): a CAPTCHA (for example Cloudflare Turnstile) or a short-lived signed form token on the embed snippet, and an alert on the `subscriber_join_throttled` log line with `cap` of `all` or `owner`.

**What it does not do: it does not make the file bucket private.** `agentweb-user-files` still allows public reads by raw URL (no S3 public access block; `docs/disaster-recovery-investigation.md` item P0-4, skipped in March until the code stopped using raw URLs). An unsigned GET of a fresh upload returned 200 on the test environment. Some keys have no random part (`screenshots/<execution id>/<epoch>.jpeg`, `blog-<ts>-repaired.html`) and can be guessed. Making the bucket private means moving every raw-URL image and link (chat, shares, CRM exports, emails) to signed links and then enabling the block: an access-policy change that needs Harsha. This change is the prerequisite (once the bucket is locked the API door must already check ownership). `/asset/:assetHash` is public by design (email images) and is unchanged.

**Known limits.** The public status and unsubscribe routes still reveal whether an address is subscribed to a task, because the unsubscribe page needs them. The join limits are per backend instance (production runs one). A throttle on one mailbox is silent, so someone can keep a victim's mailbox from receiving confirmations for an hour by submitting it for 5 tasks. `/asset/:assetHash` (public, streams any key) is untouched and defeats the policy for anyone who knows it; both it and `emma/impl/misc.ts`'s own key-ownership check need to be brought under the one policy before the bucket is locked. A confirmation link is not single-use: re-opening it within 48 hours after the row was deleted by the task owner re-adds that address. Embed snippets already pasted on customer sites keep their old "welcome email" wording but keep working (the join answer is a 2xx). The partner portal's task page lists subscribers with the person's login, so an organisation teammate who is neither the task's owner nor an admin now sees an error there (the customer portal already used the owner-or-admin route). Same-organisation members can read each other's `users/<id>/files/*` and task execution files whatever the share toggles say (before: any signed-in user could). Addresses with non-ASCII characters in the domain (rather than `xn--` form) are refused by the join form. Not in scope: ENG-2961 (an `aw_` key can activate a CRM sequence with an approver string it supplies; needs a signature from the Slack bridge and a secret Harsha provisions).

**Verification.** Backend: new and updated tests in eight files; the new tests fail against the old code. Live on the test environment: file access 59 of 59 checks pass on this change and 40 of 59 fail on the previous backend; subscribers all pass. Test-environment gotchas: it shares the production file bucket (`AWS_S3_BUCKET` unset) but uses the `Dev-` tables; its Resend key rejects `example.com` addresses; its two test accounts are in one organisation, so a stranger is a delegated session as an organisation-less `@example.invalid` user.
