## ENG-2781: Databricks-origin Zoma sign-ups skip the free-seat cap (2026-11-25)

Once the 60 free Zoma seats are taken, a brand-new customer arriving from the Databricks Marketplace listing would see "You are on the waitlist" at registration or at consent. A sign-up that starts at an OAuth client registered with a Databricks redirect URI (`isDatabricksClient`, the same registered-redirect-URI test the gateway uses to give that client's tokens the read-only tool view) is now admitted without taking a seat and without a waitlist row. Behaviour:

- `zomaSeatExemption` has a fourth reason, `databricks`, taken from a new `origin` argument on `zomaSeatExemption` / `admitZomaSignup`. It consumes nothing and records nothing on the account, so it is decided per sign-up or authorization: the same account authorizing through Claude or Cursor later is capped like anyone else.
- An admin Reject still stands: on the Databricks path the waitlist row is read once, and a `rejected` row is not exempted (the decision falls through and `admitZoma` returns the stored `rejected`, so the person sees the waitlist response). A `waitlisted` row is exempted, since the cap does not apply to Databricks, and its row is left as it was. An unreadable row throws, so the sign-up fails closed (503) rather than being exempted.
- Authorization time: `/oauth/authorize/decision` and the skip-consent fast path pass the loaded client; `admitZomaAuthorizationSignup(userId, { databricks: true, clientId })` for a Databricks client while the gate is on, the unchanged one-argument call for every other client and whenever the gate is off.
- Registration time (`/api/auth/register`, Google callback) never sees the OAuth client, so `/oauth/authorize` mints the Zoma signup intent as `<expiry>.db.<mac>` for a Databricks client (gate on only), with the mac covering the `db` marker. The portal forwards the intent opaquely, so no portal change is needed. Every other client still gets the original `<expiry>.<mac>` intent. A bolted-on marker fails validation and is refused before any seat decision (`invalid_signup_intent`, or `personal_email_not_allowed` for a personal address).
- The client's `client_name` is never consulted: a client that calls itself "Databricks" but registers no Databricks host is capped as before.
- Traceability, with nothing stored on the account and no email in the log: an exemption at authorization logs `[zoma-waitlist] Databricks-origin signup admitted without a free seat (authorization):` with the `clientId` and `userId`; at registration it logs that a signed intent marker was used (no client exists there). Nothing is logged for a grandfathered, rejected or ordinary signup.

Known limits, stated plainly: the exemption is a cost bypass that anyone can trigger by registering a client with a Databricks redirect URI (dynamic client registration is open and does not prove who owns the host, and `*.databricksapps.com` is open to any Databricks customer). Read-only binds the tokens issued to that client, not the account: the account created through the exemption is an ordinary account, it just holds no seat. `aw_` keys already skip seats (the cap is checked only at Zoma-intent registration and OAuth authorization). A rejected applicant is NOT exempted.

Flag: nothing new. Everything sits behind `ZOMA_WAITLIST_ENABLED=true`; with it off the intent is minted exactly as before and no admission call changes. There is no kill switch other than `ZOMA_WAITLIST_ENABLED=false` (which drops the whole cap) or reverting the change; no environment variable was added. Rolling deploy: a Databricks intent minted by a new instance fails validation on an old one for the minutes both run.

Not verified live: no OAuth round trip with a real Databricks client was run (offline jest only, including a cross-seam test that runs a real signed intent through the real register, Google and authorization admission with only DynamoDB faked), whether Databricks sends the RFC 8707 `resource` that marks the request as Zoma, and the deployed portal passing the longer intent through (code read only). Billing (`ZOMA_BILLING_ENABLED`) is untouched.
