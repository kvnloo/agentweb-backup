## ENG-2781: Databricks-origin Zoma sign-ups skip the free-seat cap (2026-11-25)

Once the 60 free Zoma seats are taken, a brand-new customer arriving from the Databricks Marketplace listing would see "You are on the waitlist" at registration or at consent. A sign-up that starts at an OAuth client registered with a Databricks redirect URI (`isDatabricksClient`, the same registered-redirect-URI test the gateway uses to force the read-only tool view) is now admitted without taking a seat and without a waitlist row. Behaviour:

- `zomaSeatExemption` has a fourth reason, `databricks`, taken from a new `origin` argument on `zomaSeatExemption` / `admitZomaSignup`. It consumes nothing and records nothing, so it is decided per sign-up or authorization: the same account authorizing through Claude or Cursor later is capped like anyone else.
- Authorization time: `/oauth/authorize/decision` and the skip-consent fast path pass the loaded client's registered redirect URIs; `admitZomaAuthorizationSignup(userId, { databricks: true })` for a Databricks client, the unchanged one-argument call for every other client.
- Registration time (`/api/auth/register`, Google callback) never sees the OAuth client, so `/oauth/authorize` mints the Zoma signup intent as `<expiry>.db.<mac>` for a Databricks client, with the mac covering the `db` marker. The portal forwards the intent opaquely, so no portal change is needed. Every other client still gets the original `<expiry>.<mac>` intent.
- The client's `client_name` is never consulted: a client that calls itself "Databricks" but registers no Databricks host is capped as before.
- One log line, `[zoma-waitlist] Databricks-origin signup admitted without a free seat` (no email), counts the bypasses.

Flag: nothing new. Everything sits behind `ZOMA_WAITLIST_ENABLED=true`; with it off the intent is minted exactly as before and no admission call changes. Rollback: revert the change, or set `ZOMA_WAITLIST_ENABLED=false` (which drops the whole cap). There is no separate Databricks switch.

Known limits: dynamic client registration is open, so anyone can register a client with a Databricks redirect URI (or a `*.databricksapps.com` host) and take a seat-free account whose OAuth tokens are read-only; the gate mirrors the read-only view, it does not prove the caller is Databricks. A rejected waitlist applicant is also admitted through a Databricks client, like the team and org-invite exemptions. Rolling deploy: a Databricks intent minted by a new instance fails validation on an old one for the minutes both run. Not verified: a live OAuth round trip with a real Databricks client (offline jest only), whether Databricks sends the RFC 8707 `resource` that marks the request as Zoma, and the deployed portal passing the longer intent through (code read only). Billing (`ZOMA_BILLING_ENABLED`) is untouched.
