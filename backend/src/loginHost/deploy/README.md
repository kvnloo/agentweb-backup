# Login host deploy files (ENG-2110) — NOT installed by CI; DARK

**Production worker: use `prod/install.sh` (built into a tarball by `backend/scripts/build-login-host.sh`); see `prod/README.md` for build, deploy, rollback, certificate rotation and the runbook.** The checklist below is the manual, test-instance view.

Files: `aw-login-host@.service` (host, one instance per env), `aw-env.slice.example`, `host-config.example.json`,
`claude-turn.sh` (per-turn wrapper), `aw-write-file.sh` (root helper that writes a file as a customer uid), `aw-relay-shim.js` (the tool relay's stdio MCP server, see "Tool relay" below).

Install checklist (test instance first; production needs the network-isolation PR before any external customer):
1. node 22 at `/usr/bin/node`; host build under `/opt/aw-login-host/dist`; `claude-turn.sh`, `aw-write-file.sh` there, root-owned, mode 0755.
2. Pinned Claude binary under `/opt/aw-claude/<version>/claude`, root-owned, not group/other-writable; put its sha256 in the config.
3. Homes filesystem: a fixed-size loop image mounted at `/var/lib/aw-login-host/<env>/u` with `nosuid,nodev,usrquota` (the host refuses to start otherwise); run `quotacheck`/`quotaon`.
4. `/etc/aw-login-host/<env>.json` root-owned 0600, uid range disjoint from every other env and `/etc/subuid` (the host enforces both).
5. `systemctl enable --now aw-login-host@<env>`; the socket dir `/run/aw-login-host-<env>` is the access gate (group = the backend's gid).
6. Network isolation (PR 2, mandatory): `socat` installed (`/usr/bin/socat`), `aw-net.sh` next to `claude-turn.sh` (root-owned 0755), and an `egress.allow` list in the config. Every customer unit then runs with `PrivateNetwork=yes` (loopback only) and reaches ONLY the host's allowlisting proxy (`/run/aw-egress-<env>/proxy.sock`, started and owned by the host process); the Emma tool bridge from `claude.bridgeUrl` is allowed automatically. The proxy refuses anything not on the list and any name that resolves to a private/loopback/metadata address.
7. Stopping customer processes: every customer unit stops GRACEFULLY (`KillMode=mixed`, `KillSignal=SIGTERM`, `TimeoutStopSec=<limits.stopGraceSec>`, default 10, allowed 2..12), SIGKILL only after the grace period or if the stop itself fails; revoke and the hazard alarm kill hard (the home is wiped right after). Why: the CLI refreshes an expired login in its first seconds (the server rotates both tokens, the new pair is written afterwards), and a SIGKILL in between destroys the login. DEPLOY ORDER: `limits.stopGraceSec` is a new key of a CLOSED schema; an old host binary refuses a config that has it, so deploy the new host first and only then add the key (the default needs no config change).
Config is a CLOSED schema: unknown keys fail start-up. See `host/hostConfig.ts`.

## Tool relay (ENG-2113, protocol 4)
A turn that arrives with `tools` (instead of `bridgeToken`) gets its tools without any HTTP bridge: the CLI starts `aw-relay-shim.js` (config key `claude.relayShimPath`, run with `claude.nodePath`, which must be the REAL path of node: the host refuses to start on a symlink anywhere on a trusted path, and `/usr/bin/node` is a symlink on the prod worker and the test box, so the prod template renders `/opt/aw-node/v<NODE_VERSION>/bin/node` and `install-test-host.sh` renders `readlink -f $NODE_TARGET` (the node under `/opt/aw-live/`, named at the top of the script; `/usr/bin/node` is only a link to it) after checking it is root-owned and not group/other-writable. There is no default: `claude.nodePath` is REQUIRED, because `/usr/bin/node` is a symlink on the worker and a hand-written config that fell back to it would parse and then crash-loop at the start-up trusted-path check. `install.sh` also checks, before the switch, that a customer uid can use what its unit is given: the node file executable and the shim readable by others, every directory on the way traversable) as a stdio MCP server inside the unit. Both files are root-owned and trusted-path checked at host start-up, ship in the build tarball (`files/aw-relay-shim.js`, compared byte for byte by `.github/scripts/login-host-verify-build.sh`) and are installed into the release directory by `install.sh`.
- **Per-turn socket.** For each relay turn the host creates `/run/aw-relay-<env>/<uid>/<random 128-bit id>/` (uid dir root 0711, turn dir 0700 and `relay.sock` 0600, both owned by the customer uid), listens on the socket, and only then starts the unit with `BindReadOnlyPaths=<that dir>:/run/aw-relay`. The unit must be the network-isolated shape (`PrivateNetwork=yes`, empty read-only `/run`): `unitArgs` refuses to build a relay unit without it, and refuses any directory that is not exactly one turn directory of that uid. So a unit is bound only its own `relay.sock`, at the fixed path `/run/aw-relay/relay.sock`, and another turn's relay path is absent from its mount namespace. The directory is removed when the turn's process is gone; the whole root is emptied at host start.
- **What the shim may do.** Send `{type:"call", callId, name, args}` (at most 1 MiB) and `{type:"ping"}`; nothing else, and no identity: the host maps the socket to {connection, epoch, turn} when it opens it. Frames from the host are at most 8 MiB. One connection at a time, one pending call, a token bucket, 15 s without a complete frame drops the connection. Details and the reasons are in the header of `relay/relayServer.ts`.
- **The open set.** `turn.run` `tools` (the tools open at the start of the turn: the foundation set, about 93 KB) reaches the shim as a LENGTH-PREFIXED block on stdin (a line with the decimal byte length, then exactly that many bytes, then a newline) that `claude-turn.sh` reads with `dd bs=n count=1 iflag=fullblock` (a byte-at-a-time `read` took 0.6 s for 93 KB, 3.3 s for 503 KB and about 7 s at the 1 MiB cap under bash; now about 15 ms at every size; the length is validated: digits only, no leading zero, at most `TOOL_LIMITS.maxTotalBytes + 4096`) (set `AW_TURN_TOOLS=1`), written to `$TMPDIR/aw-cfg/tools.json` (0600) in the unit's private tmp; the variable is removed before the CLI starts. Nothing about it is in argv or the environment of the CLI. Tools that become available later (a skill install) arrive as definitions on the `turn.toolResult` of the call that caused it; the host keeps the turn's visible set in memory (bounded cumulatively by `TOOL_LIMITS`), the shim adds them, announces `tools/list_changed` and waits for the CLI to re-list before it returns that result. The live check for the pilot: a chat opens with only the foundation tools; installing a skill makes its tools callable in the same run.
- **Residual risk (same uid).** Absent from the mount namespace is not the same as unreachable. A process of the SAME uid in another unit can probably open `/proc/<pid>/root/run/aw-relay/relay.sock` (`ProtectProc=invisible` hides other users' processes, not the same user's; `PrivatePIDs=yes` needs systemd >= 255 and the worker runs 252), so one customer's concurrent turns (at most 3 per login) can reach each other's relay if they race the shim for its single connection. We accept this: same-uid turns are one trust domain (one customer's own login; the plan route is own-chats-only), and the worst case is that one of that customer's own turns talks to another of their own turns' tool relay, whose calls the backend still re-validates against the run's tool list and liveness. Different uids are separated by the mount namespace AND by file ownership (0700 directory). No cheap in-code mitigation exists: Node does not expose SO_PEERCRED, and any secret handed to the shim (file, environment) is readable by the same uid through `/proc` too. **Use `PrivatePIDs=yes` once the worker runs systemd >= 255.**
- **Rollback order.** Roll the BACKEND back (or switch its relay off) BEFORE rolling the worker back to protocol 3. A backend that still sends `tools` to a protocol-3 worker gets `EINVALID` on every relay turn until its protocol re-check (`PROTOCOL_RECHECK_MS`, 10 min) notices the downgrade. A `turn.toolResult` retried after its first delivery succeeded answers `ENOTFOUND operation_unknown` (the operation was consumed): by design. The backend records that as LOST (`ToolResultLostReason` `operation_unknown` in `loginHostClient.ts` on `manan/eng-2113-relay-backend`), never as delivered: the conservative reading, because the tool may have run and the answer may not have reached the CLI.
- **Not verifiable without a real unit.** That unit B cannot reach unit A's socket is systemd's mount namespace doing its job; the host-side tests prove the path and bind construction (random id per turn, per-uid directory, the exact `BindReadOnlyPaths` property, refusal of any other directory). The live check (two turns of one uid, `ls /run/aw-relay` and a connect attempt in each) belongs to the pilot rehearsal.
- **Deploy.** The worker deploys first. Config keys `claude.relayShimPath` and `claude.nodePath` are new in the CLOSED config schema (the shim path has a default, the node path is required); an older host binary refuses a config that has them, so use the release's own rendered config (`install.sh` does). The backend's accepted worker protocols must include 4 before this worker goes live.

## Hostile input and crash safety (ENG-2113 security review)
Everything a customer's unit controls (the shim's frames, the CLI's stdout, the bodies of requests) is treated as hostile data that must never make the root host throw out of a timer or an event handler: an uncaught exception ends the process for EVERY customer.
- **Depth.** A shim frame nested deeper than `MAX_FRAME_DEPTH` (33: the frame, `args` and 31 more levels) is dropped BEFORE it is parsed, by a single pass over the bytes (`relay/bounds.ts`); a line of the CLI's stdout deeper than 64 is cut where it passes the limit and replaced by a fixed placeholder line before the runner parses it. Values forwarded to the backend from the stream (the informational `tool-use` input) deeper than 32 or larger than 1 MiB become `{"_truncated":"depth"|"size"}`; ids and names longer than 256 characters drop the event. A `tool-call` input is NEVER truncated: it is executed by the backend, so an over-deep one is refused (the shim gets an internal error), not replaced.
- **No stringify of hostile data.** Memory accounting uses the frame size the relay measured or an iterative estimate; `JSON.stringify` of a value from the shim or the CLI is gone from the host (it throws a RangeError past about 5,000 levels).
- **Every callback is guarded.** Relay data handlers and timers, the adapter's relay callbacks, the manager tick and event serialization catch, log a fixed code and take a safe outcome (drop the connection; answer the call with an internal error and close the endpoint; abort the turn). A last-resort `uncaughtException`/`unhandledRejection` handler logs one fixed code (never the error text or stack, by design: they can quote customer input, so diagnosing a real crash needs a reproduction, not the journal) and exits 1, exactly when and how Node would have, so `Restart=on-failure` still restarts the host; it never keeps the process running.
- **Linear line reader.** The relay assembles newline-delimited frames in time linear in the bytes received however a unit chunks them (`LineAssembler`: the newline is searched for only in the new chunk, pending pieces are copied into a list and joined once per completed line, the 1 MiB cap is enforced on the running total). The naive concat-and-rescan loop cost about 1.8 s of the shared host's event loop for one 1 MiB line sent in 64-byte writes; this one costs about 8 ms.
- **Never-reading peer.** More than two maximum frames queued for a shim that does not read cuts the connection and ends the pending call.
- **Log flood.** Violation lines are throttled per endpoint and per code (5 per 10 s), and host-wide (50 per 10 s), with a count of the suppressed ones reported afterwards.
- **Failure-text patterns** (`classifyFailureText`) search only the first 8 KiB: their unbounded gaps are quadratic on a megabyte of near-matches.
- **Crash loop.** The unit has `Restart=on-failure`, `RestartSec=5`, `StartLimitIntervalSec=120`, `StartLimitBurst=5`: five starts within 120 s (a crash every ~5 s reaches that in ~25 s) put the unit in `start-limit-hit`; systemd stops restarting it, `OnFailure=aw-login-host-failed@%i` only echoes a line to the journal, and the worker stays DOWN for every customer until an operator runs `systemctl reset-failed` and starts it. That is why a crash a customer can trigger at will is a blocker, and why the unit is NOT loosened: unlimited restarts would instead stop every customer unit (`stopEnvironment`) on each start. Starts that fail the pre-switch trusted-path check never get that far: `install.sh` refuses them before the switch.
- **Sizing answers.** `turn.toolResult` bodies are capped at 8 MiB and the shim frame at 8 MiB, but `content` is counted in CHARACTERS by the schema (4,000,000) and JSON-escaped on the wire: a result full of control characters or non-ASCII is several times larger than its character count. The backend must size answers by serialized BYTES (UTF-8 and escapes included), not characters; the host refuses a result whose frame would exceed 8 MiB with `EINVALID result_too_large` and leaves the operation pending.
- **Availability caps (round 5, security review of e4ae1c38b).** A hostile CLI or unit can no longer slow the shared host by volume: (1) the CLI's stdout goes through ONE line authority (`LineLimit`): only a complete JSON object (first non-space byte `{`, last `}`, balanced outside strings) is forwarded to the runner, everything else (junk, a lone `{`, an unterminated object) is dropped before the runner JSON.parses it and throws; `\r` and `\r\n` are rewritten to one `\n` so the scanner and the runner agree on lines; junk and blank lines are charged to a token bucket (burst 200 lines / 1 MiB, refill 50 lines and 128 KiB a second) and event lines to another (burst 5,000, 2,000 a second): past a bucket the CLI is killed (`stdout_flood`). (2) A `rate_limit_event` keeps at most 16 windows and short status words; any message looks at its first 32 content blocks; the queue weight of every event is its real payload. (3) The relay socket: after 32 refused connections, or once the turn can accept no more, the listener is CLOSED (the kernel refuses further connects; a connect flood of 3,000 attempts accepted-then-destroyed 1,261 connections before and 124 after, the rest failing at the kernel); a byte budget (4 MiB burst, 2 MiB/s) next to the frame bucket; a frame with more than four keys is dropped before its keys are sorted; at most 500 calls are relayed per turn (the next gets `call_limit`, logged once); the adapter hashes at most 8 MiB per turn for matching a call to its model message and never a call over 64 KiB (matched by name only). The shim keeps ONE connect in flight, so a call racing its own start-up connect no longer gets the live connection refused.
- **What the CLI is told (relay turns only).** The unit's environment carries `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` (= `TOOL_LIMITS.maxDescriptionBytes`, 48 KiB; the CLI would otherwise shorten a description at 4,096 characters), `MAX_MCP_OUTPUT_TOKENS` (the CLI truncates a result above 25,000 tokens by default: here two bytes per token of `RELAY_RESULT_MAX_BYTES` (300,000: the same cap in-process Emma applies, shared with the backend), plus 1,600 per image; deliberately not the 8 MiB frame cap, which would remove the CLI's protection of the model's context) and `MCP_TOOL_TIMEOUT` (the turn's remaining deadline in ms, at least 1000, so the host's clock is the one that ends a call). Names confirmed in the strings of CLI 2.1.314; legacy turns set none of them. `MCP_TIMEOUT` is the start-up timeout of the server, not a call limit, and is not set; `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` (30 minutes for stdio) is refreshed by the shim's progress notifications.
- **Shared change in `claudeCliRunner.ts`.** `services/funding/claudeCliRunner.ts` carries a small ADDITIVE change used by this branch and the backend branch (an optional stdio MCP server, `extraLines`, `sameMcpServer`); legacy callers are unchanged. The file is byte-identical on `manan/eng-2113-relay-host` and `manan/eng-2113-relay-backend` (diffed), so the two merge cleanly in either order.
- **Stream shape rules (round 6).** Event lines are charged by BYTES too (burst 64 MiB, 4 MiB/s: honest traffic is a few big tool-result echoes (a 6 MB image echoed twice is 12 MB) then quiet); a line with more than 150,000 values (commas, objects, arrays outside strings; honest events have a few thousand at most) or nested deeper than 64 is replaced by the fixed placeholder and charged to the junk bucket, as are blank and whitespace-only lines. A single such line over 1 MiB of junk, or 200 of them within the burst, ends the stream (`stdout_flood`). Measured through the real adapter, readline and JSON.parse: 16 MB array of zeros 488 ms/+357 MB per line before, dropped now; 15 MB array of `{}` 1.73 s/+1.3 GB before, dropped now; 1 MiB string lines ended after the 32 MiB burst instead of never; 131,040 deep lines and parse exceptions in 3 s before, none forwarded and the stream ended within the junk burst now.
- **CPU meter.** Every turn has a token bucket of event-loop milliseconds (burst 1000 ms, refill 50 ms/s) charged by min(wall time, CPU time of the thread) of each synchronous section that handles the unit's bytes (the CLI's stdout including the whole readline/JSON.parse/callback chain downstream, its stderr, the session's event work, each relay socket read and the answer path) plus a fixed 0.08 ms per read; reads are limited to 200/s per stream. Empty means the CLI is killed (`cpu_budget`); on any trip the raw pipes are closed before the kill. A flat-out hostile turn is dead within about 3 s; one that paces itself at 5% is not killed, so with production's `maxTurnsPerHost` of 8 such turns can hold about 40% of the loop (ARITHMETIC, 8 x 5%, not a measurement; the code default of 12 would give 60%). See the dev note for the measured numbers and the capacity statement.
- **Result threshold per tool.** The CLI persists a tool result above a per-tool threshold to a file and shows the model a ~2 KB preview, whatever `MAX_MCP_OUTPUT_TOKENS` says. The shim lists every tool with `_meta {"anthropic/maxResultSizeChars": 300000}` (= `RELAY_RESULT_MAX_BYTES`), so a result the relay can deliver arrives whole.
- **Known residual.** The same-uid `/proc/<pid>/root` reach to a relay socket is not closed by any of the above; it is measured by live group B on the test box.
