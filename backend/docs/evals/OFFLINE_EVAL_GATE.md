# Offline eval suite and regression gate (ENG-2145)

Implements ENG-782 items 2 and 3 under the contract Harsha approved on 2026-08-31, and decision D4 of
ENG-2128. The gate runs on Atem or against staging. It never gates a merge in GitHub Actions: GitHub CI runs
builds and invariant checks only, and product suites never gate merges there (repo `CLAUDE.md`). The one
GitHub job that runs the suite (below) reports and cannot fail on the verdict.

## Run it

```bash
cd backend
# Local, deterministic, no credentials (the committed baseline):
npx ts-node --transpile-only src/loops/scripts/runOfflineEvalSuite.ts --target local
# Staging: a finished Okareo test run against the staging target (needs OKAREO_API_KEY, OPS-6 / ENG-2151):
npx ts-node --transpile-only src/loops/scripts/runOfflineEvalSuite.ts --target staging \
  --baseline src/loops/eval/baselines/<staging-baseline>.json --okareo-run <test-run-uuid> [--golden] [--out result.json]
```

`--target production` is refused. Exit code: 0 unless the gate blocks (1 regression, 2 unavailable); 64 for
a usage error. The printed Markdown report is meant for the PR or the run log; `--out` writes the full
result as JSON.

## What it compares

| Source | Metric | Kind | Needs |
| --- | --- | --- | --- |
| ENG-591 registered replay cases (`failureReplayCatalog.ts`) | `failure-replay:<grader>` | deterministic | nothing |
| ENG-1312 reply-length fixtures | `replay-fixture-length` | deterministic (placeholder inputs until OPS-2 links real sessions) | nothing |
| The same fixtures regenerated by a candidate prompt/model | `replay-fixture-length:candidate` | probabilistic | a staging runner |
| Golden set, grader vs human labels (test split) | `golden-agreement:<grader>:<criterion>` | probabilistic | `EVAL_GOLDEN_CASES_TABLE` (OPS-2, ENG-2147), `--golden` |
| Okareo checks on a staging test run | `okareo:<check>` | probabilistic | `OKAREO_API_KEY` (OPS-6, ENG-2151), `--okareo-run` |

Each baseline file (`src/loops/eval/baselines/*.json`) is versioned and records, per metric: grader id and
version, kind, n, passes, the threshold (largest allowed drop in pass rate) and `minN`. Record a new one
with `--write-baseline <file> --baseline-id <id>` from a clean run and commit it through a PR.

- **Deterministic metric:** any drop past its threshold (normally 0) is a regression.
- **Probabilistic metric:** a regression needs the drop to exceed the threshold **and** the 95% interval of
  the change (Newcombe, from Wilson intervals) to lie wholly below zero. A dip within sampling noise is not
  a regression.

## Verdict and fail-closed rules

`pass | regression | unavailable`. The verdict is `unavailable`, never `pass`, when a source is
unavailable, times out, is unauthenticated or returns malformed results; when a baseline metric has no
result (including a source that is not configured); when the grader version changed since the baseline;
when the run decided fewer than `minN` cases; or when the baseline was recorded on another target.

## Report-only until validated

A metric may block only if its grader passes `evalRegistry.mayGate` (a recorded human-agreement
validation). A metric can never block if it is a security metric judged by an LLM, or if its inputs are
synthetic placeholders. Blocking also needs `EVAL_GATE_BLOCKING=true`.
Today no registry grader passes `mayGate`, so the gate is report-only: it computes and prints the verdict
and blocks nothing. To switch to blocking:

1. Validate a grader with the ENG-2136 agreement harness on the golden set, and record
   `validation: { kappa, n, date, evidence }` in `evalRegistry.ts` (kappa >= 0.6, n >= 30, http(s) evidence).
2. Record a baseline that contains that grader's metric (staging, Okareo or golden set).
3. Set `EVAL_GATE_BLOCKING=true` in the Atem/staging runner environment. From then on a regression on that
   metric, or any unavailable result, exits non-zero.

In blocking mode, only an explicitly recorded human bypass lifts a block:

```bash
--bypass-by "<human name>" --bypass-reason "<why, 10+ chars>" --bypass-ticket ENG-<n>
```

Automation identities (bots, CI, Claude, cron) are refused. The bypass is stored in the run output with the
time, and the verdict is not changed. Paste that output into the PR or the ticket.

## Triggers

- **PRs (automatic, report-only, ENG-2195):** `.github/workflows/offline-eval.yml` runs
  `--target local` on a pull request that changes a prompt, model-registry, skill or eval source (the
  workflow's `paths` list). It needs no credentials and makes no network or LLM call. It writes the report to
  the job summary and raises a warning annotation when the verdict is not `pass`, but it always exits 0: it
  strips `EVAL_GATE_BLOCKING`, is its own workflow, waits on nothing and nothing waits on it, and is not a
  required check. `.github/scripts/offline-eval-report.test.sh` pins that shape. The local suite covers the
  replay cases and fixtures only; a prompt or model change still needs the staging lane for a real verdict.
- **Staging runs:** run the CLI on Atem. A PR that changes prompts, models, skills or tool schemas
  should cite the staging report.
- **Nightly:** `cron/failureReplayNightlyCron.ts` replays the registered cases at 04:30 UTC and files a
  regression once through the ENG-240 intake. It runs only with `FAILURE_REPLAY_NIGHTLY_ENABLED=true`
  (ENG-591 AC2).
- **Database edits:** every AW-Settings write to a prompt, model, judge, work-plan, skill or tool setting
  (`settingsService`) records a marker. So does every skill create, update, delete, approve or sync in
  `skillService` (ENG-2195), whoever the caller is: the admin routes, the user skill routes, Emma's skill
  tools, agent mode and the seed/patch/rewrite scripts. A create or update is marked only when it changes
  `systemPrompt`, `toolNames`, `llmModel`, `isPublished` or `maxIterations` (compared against the row the
  write replaced); a delete is marked only when the skill existed. Each marker is
  one `eval_needed` row in `Dev-AW-LoopEvents` (loopId `eval-gate`). It holds the setting name or skill
  id, the change kind and a 12-character sha256 of the new value, never the text. The marker write is
  best-effort: it never blocks the edit, and a failed marker write leaves that edit out of the feed. `--changes-since <iso>` lists the markers; `EVAL_CHANGE_MARKERS_ENABLED=false` turns
  them off.
- **Marker consumer (ENG-2195):** `cron/evalMarkerSuiteCron.ts` checks hourly for markers written since its
  last run. When there are any, it runs the deterministic local suite and records one `eval_suite_verdict`
  row in `Dev-AW-LoopEvents` (loopId `eval-gate-runs`): verdict, mode, marker count and categories, the
  per-metric status, and `markersThrough`, which is the next run's cursor. It is report-only: a non-pass
  verdict is logged as a warning and nothing is filed. It runs only with `EVAL_MARKER_SUITE_ENABLED=true`.

file (`loops.agentModeWiring.test.ts`), and `refresh-model-catalog.yml` runs `modelCatalogRefresh.test.ts`
and `llmPricing.test.ts`. None of the env vars that turn on a live suite is set in any workflow. So the
"before/after Actions minutes" in ENG-782 AC3 is already zero for LLM suites. The saving came from the
earlier Atem policy, not from this PR.
